Sinh viên CNTT thường làm bài tập đơn lẻ trên LeetCode/HackerRank, thiếu khả năng giải thích tư duy logic bằng lời nói (Think-aloud protocol) và dễ lúng túng khi người phỏng vấn đặt câu hỏi xoay quanh edge-cases.

⚠️ Thiếu phản hồi cá nhân hóa định lượng

Các buổi Mock Interview truyền thống phụ thuộc vào chuyên gia tốn kém chi phí, khó linh động thời gian và không lưu vết dữ liệu năng lực theo dạng ma trận toán học $C[k, e]$ qua từng giai đoạn ôn luyện.

1.3 Mục tiêu đề tài

Xây dựng nền tảng web hoàn chỉnh DevOrDead cung cấp:

  • Môi trường mô phỏng phỏng vấn giọng nói hai chiều thời gian thực (độ trễ < 350ms) tích hợp AI Voice Intercom.
  • Môi trường thực thi và chấm mã nguồn an toàn tuyệt đối qua Docker Sandbox (cgroups v2).
  • Hệ thống đánh giá ma trận năng lực toán học $C[k, e]$ tự động cập nhật lộ trình học thích ứng sau mỗi buổi làm bài.

Kiến trúc phân tầng dịch vụ (Multi-tier Architecture)

Tầng kiến trúc Thành phần & Công nghệ chính Trách nhiệm đáp ứng chức năng
1. Tầng Trình diễn (Presentation) Web SPA (Next.js / React), Monaco Code Editor, Web Audio API, Audio Waveform Visualizer. Hiển thị Roadmap, phòng phỏng vấn voice trực quan, editor gõ code và bảng điều khiển quản trị (F01–F18).
2. Cổng kết nối (API Gateway) Nginx Reverse Proxy, SSL Termination, RESTful API Router, WebSocket Gateway Manager. Điều phối kết nối mạng an toàn, duy trì kết nối hai chiều real-time cho âm thanh và đồng bộ editor (F05, F11, F12).

4. Thực thi Chuyên biệt (Runners) AI Orchestration Pipeline (OpenAI/Gemini API, STT/TTS) & Isolated Docker Sandbox Runner (cgroups v2). Chuyển đổi âm thanh voice, sinh phản hồi phỏng vấn và thực thi chấm mã nguồn an toàn trong container (F05, F09, F11, F12).
5. Dữ liệu & Lưu trữ (Data Layer) PostgreSQL 15 (Relational Data) & Redis 7 (In-memory Session Store, Cache, Pub/Sub). Lưu trữ toàn vẹn dữ liệu người dùng, bài tập, lịch sử nộp bài và trạng thái phiên phỏng vấn trực tiếp (F01–F18).

3.2 Yêu cầu phần cứng (Hardware Specifications)

💻 Yêu cầu phía Người dùng (Client)

• Thiết bị: PC / Laptop (Windows, macOS, Linux).

• CPU & RAM: Tối thiểu Dual-Core 2.0 GHz, RAM ≥ 4 GB (khuyến nghị 8 GB).

• Ngoại vi: Microphone thu âm rõ tiếng, Loa ngoài hoặc Tai nghe hoạt động tốt.

• Internet: Băng thông ≥ 5 Mbps (khuyến nghị ≥ 15 Mbps, ping ≤ 50ms).

🖥️ Yêu cầu phía Máy chủ (Server & Cloud)

• Application Node: 2 vCPU, 4 GB RAM, 30 GB SSD (Ubuntu 22.04 LTS).

• Database & Redis: 2 vCPU, 4 GB RAM, 20 GB SSD có sao lưu định kỳ.

• Sandbox Execution Node: 4 vCPU, 8 GB RAM, 40 GB SSD (Docker cgroups v2).

• Mạng máy chủ: Tối thiểu 100 Mbps đối xứng.

#146. Triển khai bộ nhớ đệm LRU Cache
Medium Hash Table Doubly-Linked List Design

Thiết kế một cấu trúc dữ liệu tuân thủ các quy tắc của bộ nhớ đệm Least Recently Used (LRU) Cache.


Cần hiện thực hóa lớp LRUCache với các phương thức:

  • LRUCache(int capacity): Khởi tạo bộ nhớ đệm với dung lượng dương.
  • int get(int key): Trả về giá trị của key nếu tồn tại, ngược lại trả về -1. Thao tác này đưa phần tử lên vị trí mới nhất.
  • void put(int key, int value): Cập nhật giá trị nếu key đã có, hoặc chèn cặp key-value vào bộ đệm. Nếu số lượng vượt quá capacity, hãy thu hồi (evict) phần tử ít được sử dụng nhất.

Yêu cầu độ phức tạp: Tất cả các hàm get và put phải chạy với độ phức tạp thời gian trung bình O(1).

Ví dụ 1:
Input:
["LRUCache", "put", "put", "get", "put", "get", "put", "get", "get", "get"]
[[2], [1, 1], [2, 2], [1], [3, 3], [2], [4, 4], [1], [3], [4]]
Output: [null, null, null, 1, null, -1, null, -1, 3, 4]

Ràng buộc hệ thống:

  • 1 ≤ capacity ≤ 3000
  • 0 ≤ key ≤ 10^4
  • 0 ≤ value ≤ 10^5
  • Tối đa 2 × 10^5 lệnh gọi hàm get và put.
